## 1. 目标与推进方式

运行前提：单作者、本机应用与数据、允许云端模型 API、文件优先且允许 SQLite。首个产品界面为 Web，后续 Electron 复用同一核心交付。

已确认执行顺序：**先封装 AI 与配套业务后端，通过统一接口测试验收；再集中设计、开发前端并接入这些接口。**

2026-11-18 用户确认：先完成核心后端闭环，再开发前端，之后补充额外后端能力。核心路径为 P0 → P1/P1.1 → P2/P2.1 → P3 → P7 → P8；P4—P6 保留编号，作为前端之后的扩展。每阶段通过 HTTP / SSE 接口测试和必要的真实模型评测交付，不依赖 Web 页面。第一份可运行交付物是 P1 本机 Agent 服务与可重复执行的接口用例。

P3 形成“打开小说工作区 → 保存 Markdown 资料 → 用户大纲原文留档 → 按需丰富大纲候选 → 读取正式资料/具体冲突讨论 → 章节或选区候选 → 逐处采纳/拒绝 → 恢复/导出”的后端闭环。完成 P3 的核心后端整体接口验收后，进入 P7 集中开发前端；P7 才形成作者可直接使用的创作产品。原 P7 本地试用顺延为 P8。

前端是独立重点阶段，需要完成交互设计、视觉设计、编辑体验、生成反馈、候选对比和实际使用验证。接口返回成功只证明后端可用，不能替代前端体验验收。

为减少后续返工，后端接口设计先梳理核心用户操作及所需信息：作者正在编辑什么、提供哪些参考、生成到什么状态、如何比较候选和撤销采纳。此时只形成操作流程与接口需求，产品界面代码集中在 P7 实现；P7 发现真实交互缺口时，补充接口并同步回归测试。

恢复口径统一为：重新打开已保存会话、查看已保存候选并由用户继续。未完成请求可重新发起，不要求自动续跑剩余步骤或精确恢复 token。普通等待按结束本轮、下一条消息继续实现。

### 2.1 后端阶段的统一交付要求

- 能力通过同一本机服务按业务提供 HTTP / SSE 接口，前端无需直接访问 Pi、文件或数据库。
- 接口契约明确请求、响应、资源标识、当前状态、错误及流式事件；业务结果与可操作状态要能直接供页面使用，不把 Pi 内部事件原样当作长期前端协议。
- 每项能力附请求示例、测试数据、预期结果和可重复运行的接口测试；测试从公开接口发起，覆盖完整操作链。
- 后续所有新增或修改接口必须按模块注册到接口试验台，补齐用途、参数示例、字段和事件说明，并从页面实际调用验证结果；同步维护目录覆盖测试与阶段验收记录。未完成登记和验证，不得标记阶段完成。
- 流式接口验证内容增量、工具状态、完成、失败和停止；重新查询可获得当前会话及结果。状态由本机服务与 SDK 提供，不为此新建持久化工作流。
- 接口行为可用确定性测试验证；模型连通性和输出效果另用真实模型验证，分别记录结果，不能以 Mock 替代真实接入结论。
- API 说明与用例随实现维护；接口测试通过是进入下一后端阶段的条件。P3 汇总核心全链路回归与接入资料，作为 P7 的进入条件。

LangGraph、直接 agent-core 替代路线和持久化工作流不列入当前必做项；只有 SDK 实测出现具体阻塞才重新评估。P0 验证能力已用于 P1 后端接口。

## 4. P1：通用 Agent 后端与统一接口

目标：将 Pi SDK 已有能力封装为本机服务，通过接口独立使用和验证。

任务：

- [x] 初始化 apps/server、agent-pi、contracts 和接口测试；此阶段不初始化产品前端。
- [x] 接入 SDK 模型配置、系统提示、工具集合、会话目录及事件。
- [x] 提供会话创建、列出、打开、消息提交、消息/状态查询接口，复用 JSONL 持久化。
- [x] 提供流式订阅、停止与模型配置接口，明确消息标识、事件类型、完成/中断状态与错误响应。
- [x] 注册一个只读测试工具；参数格式校验、工具循环、压缩、有限重试和 abort 直接复用 SDK。
- [x] 支持断开订阅后重新查询会话与当前状态，不要求持久化每个 token。
- [x] 按普通多轮消息处理候选选择；只用 SDK 自定义条目标记请求开始/结束以识别崩溃中断。
- [x] 返回可获得的模型用量和错误，保留必要日志；密钥留在本地核心。
- [x] 交付接口说明、请求示例、测试数据与 HTTP / SSE 自动化用例。

验收：

- 从干净检出按说明启动服务，不启动 Web 即可通过公开接口完成多轮对话和测试工具调用。
- 重启后通过接口列出、读取并继续已有会话，不同会话不串用。
- 流式响应包含预期的内容、工具和结束事件；停止接口能中止当前生成，查询结果状态与之相符。
- 中断后能读取已保存消息；生成候选后结束本轮，重启再提交选择仍能继续。
- 常见配置缺失、参数错误、模型失败可从响应或事件判断，不暴露密钥。
- 修改提示词或注册新的只读工具即可使用，不修改 Agent 执行循环。
- 确定性接口测试和真实模型验证均有记录；无需小说记录、任务库、队列或检查点系统。

主要位置：apps/server、packages/agent-pi、packages/contracts、tests/api、docs/api。确定性接口测试与真实 HTTP 验收通过，详见 [P1 验证记录](p1-validation.md)；下一阶段为 P2。

2026-11-17 全量复核：上述 9 项任务均已完成，P1 当时的 8 个接口（P1.1 完成后为 16 个）已注册到试验台并完成浏览器联调，用户已确认接口与控制台无问题。试验台作为后续阶段的接口验证入口；P7 产品前端范围不变。

## 5. P2：Markdown 工作区、版本与候选基础

目标：以真实 Markdown 文件为正式资料，通过接口完成文件操作、版本和逐处采纳。用户已确认旧 JSON 资产草稿无用，直接清理并重做，不保留兼容。实施细节见 [P2 计划](plans/p2-implementation.md)。

任务：

- [x] 登记并打开用户指定小说文件夹，列出、读取和保存实际 Markdown；文件不依赖固定中文目录名。
- [x] 正文、大纲、五栏人物卡和作品要求都使用版本化 Markdown；选区采用 UTF-16 原文位置。
- [x] 创建候选、后端计算差异、逐处采纳或拒绝；记录部分处理状态与幂等结果，重启后继续。
- [x] 重新读取并检查外部编辑，保护期间改稿；验证 Windows 文件并发提交行为。
- [x] 提供保存结果/版本、历史查询和恢复接口；恢复创建新版本，保留历史。自动保存触发与状态展示由 P7 实现。
- [x] 保存手工 Markdown 人物卡、大纲、章节和作品要求；不强制结构化人物事实或编辑器文档。
- [x] 采用文件仓储：内部 JSON 保存登记/候选/历史清单，独立 Markdown 保存快照；没有 SQLite，暂无迁移。
- [x] 在本机业务接口中校验书籍与正文归属，防止不同小说串用；首版不开发多用户账户体系。
- [x] 提供原始 Markdown 导出与资产备份，按备份说明验证恢复。去除 Markdown 语法的 TXT 等额外格式后置。

验收：

- 使用接口创建一本小说、两个章节和人物设定，重启后查询内容完整。
- 同一正文版本的竞争保存被检测，不静默覆盖已保存的新版本。
- 能从历史版本恢复，且能再次查看恢复前的内容。
- 两本书的正文和设定互不串用；导出内容与选定正文版本一致。

主要目录：`domain`、`application`、`storage`、`server/routes`、`contracts`、`tests/api`。

2026-11-18 验收：全量自动化 40/40 通过；P2 新增 17 个接口在试验台完成 25 次实际请求；类型检查、构建和 Windows 文件占用/进程中断验证通过。详见 [P2 验收](p2-validation.md)。本阶段不含技能管理、小说聊天关联或模型生成；核心后端仍需 P2.1 和 P3。

## 6. P3：创作后端闭环

目标：通过接口完成按详细大纲生成章节、带设定和样文的续写/选区修改、逐处采纳及恢复，并完成核心后端整体验收。此阶段交付后端闭环，P7 再接入作者使用的界面。

任务：

- [x] 复用 P1 的会话、消息、工具和流式接入，使用 P2/P2.1 工作区、聊天关联与候选服务，保留通用会话协议。
- [x] 注册小说工具：读取场景、人物设定、作者样文和创建修改提案；经业务服务校验作者、书籍与版本。
- [x] 实现最小上下文编译：当前选区、邻近正文、作者选定的人物/设定、场景目标和样文；包含来源与版本。
- [x] 实现“详细大纲生成章节”“续写场景”和“选区改写”流程，明确步骤终点和输出预算。
- [x] 实现最小审校：依据本次上下文检查明显设定与视角冲突，返回问题与证据；不承诺此时具备全书检查能力。
- [x] 提供创作请求、生成事件、候选查询与参考材料接口，复用 P1 的流式、停止和错误协议。
- [x] 通过 P2 候选接口返回原稿、实际差异和每处状态；只允许模型创建候选，不注册正式稿采纳工具；差异界面在 P7 实现。
- [x] 保证拒绝或未采纳内容不进入正式小说资料；候选产物可保存供作者查看。
- [x] 保存候选提案及来源版本；重启后可查询并采纳原候选，源版本变化时返回明确冲突信息。
- [x] 记录作者样文、明确风格要求、采纳/拒绝以及最终修改结果；此时不自动推断长期偏好。

验收：

- 创作接口自动带入已登记、选定的设定，响应可查询本次参考材料及来源版本。
- 续写和改写均可生成提案、采纳、拒绝及回退。
- AI 生成期间通过保存接口更新正文，旧提案不能覆盖新版本；重复采纳只产生一次提交。
- 测试客户端断开后重新查询会话和候选；停止不会自动提交正文；服务重启后可读取已保存候选并继续采纳/拒绝。
- 准备至少 10 个合成或获授权的小说样本，覆盖续写、对白、设定与视角；记录同模型普通聊天及当前上下文方案的结果、耗时和用量，作为后续改进基线。

范围说明：此阶段的设定关联以作者选择和直接读取为主；自动长篇召回、完整知情状态重建和记忆提取在 P4—P5 完成。通过公共接口接入业务后，P1 的通用 Agent 验收仍应通过。

实际实现：`application/src/writing.ts` 编译上下文与审校，`server/src/writing.ts` 适配工具，复用 `agent-pi` 请求资源与元数据；没有为当前规模新建独立 context 包。接口、测试与样本位于 `contracts`、`tests/api`、`evals`。

2026-11-18 验收：55 项独立接口测试与 3 项目录/流测试通过；试验台完成 32 项检查、覆盖所有四个新接口。修正 P1 演示资源污染后，10 组真实对照全部流程通过，7 组候选、2 组冲突等待、1 组原文取证。结构化耗时和 token 更高，文本不宣称普遍优于普通聊天；详见 [P3 验收](p3-validation.md) 和 [接入说明](api/p3-writing.md)。

## 7. P4：长篇记忆与事实来源后端

目标：从正式正文中提取可检查的记忆，并正确表达“谁在什么时候知道什么”。

任务：

- [ ] 提供 TXT/Markdown 导入解析、切章预览数据与确认接口，确认后保存原稿版本。
- [ ] 建立实体及别名、客观断言、文本陈述、角色信念和知情记录。
- [ ] 区分故事时间、叙事位置与数据版本；支持相对先后及未知时间。
- [ ] 实现章/场景摘要、事件和人物状态提取，保存来源段落、引用及提取配置。
- [ ] 提供候选事实查询与批量审核接口，返回硬设定冲突、重要人物变化及来源。
- [ ] 正文或设定变化后标记派生数据过期并重建；发布结果前校验源版本。
- [ ] 提供事实冲突查询与处理接口，支持修改正文、修改设定或保留有意矛盾的决定。

验收：

- 第 20 章才获知的秘密，不会出现在第 12 章该角色的已知信息中。
- 倒叙场景按故事时间和叙事位置分别解释，不将章节顺序直接视为事件时间。
- 人物伤势、地点和物品归属能够按目标时点重建。
- 被拒绝的候选稿不产生正式事实；每条确认断言可定位原文或作者设定。
- 修改来源后旧摘要和断言不再作为当前有效证据，晚到的旧任务结果不能覆盖新结果。

主要目录：`domain/story-bible`、`context/visibility`、`context/provenance`、`application/writing`、`storage`、`server/routes`、`tests/api`。

## 8. P5：长篇上下文检索与一致性后端

目标：自动选取相关资料，同时控制时间、视角、版本和上下文预算。

任务：

- [ ] 建立场景/段落切块及章节、卷、全书摘要的分层组织。
- [ ] 建立中文词项、人物别名与向量索引；独立选择并验证 embedding 接口。
- [ ] 实现混合召回、去重和排序；硬约束经结构化查询纳入。
- [ ] 对所有召回路径落实作者、书籍、有效版本及可见性过滤。
- [ ] 区分规划与写作上下文；未来计划按当前任务需要提供，避免视角泄漏。
- [ ] 实现预算裁剪、必要材料超预算时的拆分策略及证据不足提示。
- [ ] 通过接口返回本次参考与选择原因，接受固定/排除材料的参数；固定材料仍遵守可见性与版本约束。
- [ ] 扩展人物、时间线、伏笔及设定一致性检查，提供可定位证据。

验收：

- 固定测试集中，指定硬约束全部进入适用任务上下文；禁止泄漏的信息不会进入对应写作视图。
- 将应召回的关键原文标为标准答案，报告召回覆盖率与失败样例；首轮测量后登记发布阈值，再进行优化，不能事后为结果降低阈值。
- 在目标长篇样本上，组装结果满足预算且能说明被裁剪材料；关键资料无法放入时不会静默丢弃。
- 来源更新后，检索不会继续返回失效内容作为有效依据。
- 同模型对比普通聊天、仅正文检索及完整上下文，记录事实错误、采纳情况和运行成本。

主要目录：`context/retrieval`、`budget`、`visibility`、`storage/search`、索引重建流程、`server/routes`、`tests/api`、`evals`。

## 9. P6：后续高级风格与规划扩展

目标：在核心前端之后补充高级风格、审校、偏好学习与规划；P3 已承担首版质量、接口整体验收及前端接入资料。效果评测通过接口生成产物并组织人工盲评；实际界面的操作效率在 P7—P8 验证。

任务：

- [ ] 提供作者、作品、场景三层风格配置接口，明确跨作品偏好需主动启用。
- [ ] 按场景类型选取作者认可的样文，保留来源和版本。
- [ ] 增加对白声音、情绪解释、视角漂移、重复表达等审校维度及局部修改建议。
- [ ] 为自动修订设置次数与用量上限，达到上限时返回剩余问题。
- [ ] 从采纳/拒绝及人工修改积累反馈；重复偏好经作者确认后生效，支持撤销。
- [ ] 按实际需求增加自动大纲规划与复杂多场景编排（按详细大纲生成章节已在 P3）；任务内部候选场景可供后续场景引用，保持与正式资料隔离。
- [ ] 建立盲评流程，比较同模型下不同上下文与风格方案，记录模型和提示词版本。

验收：

- 同一作者两部作品的样文与偏好不会自动串用。
- 可通过接口查询、修改和关闭已记录偏好；一次改动不会直接变成全局规则。
- 审校能定位原文并说明修改理由，默认保留未涉及的内容。
- 在冻结的样本及配置上完成至少两轮对比，报告盲评偏好、采纳率、修改量、完成时间及成本；如未改善，保留失败结论并调整方案，不能仅凭模型自评分通过。
- 多场景候选稿拒绝后，其实体和剧情不会进入正式检索。

主要目录：`domain/style`、`application/writing/prompts`、`application/writing`、`server/routes`、`contracts`、`tests/api`、`evals`。

## 10. P7：前端体验设计、实现与接入

目标：把已验收的后端能力组织成作者愿意持续使用的 Web 创作工作台。前端是独立重点交付，不能以接口联通代替体验完成。

执行顺序：用户操作流程与信息架构 → 关键交互和视觉方案 → 页面实现 → 真实接口接入 → 连续创作体验验证。沿用前期操作需求，设计阶段核对接口数据是否足够。

任务：

- [ ] 梳理建书/导入、编辑正文、配置材料、发起生成、比较候选、采纳/拒绝、版本回退的连续操作路径。
- [ ] 完成书架、编辑工作台、AI 助手、设定/来源、候选对比、版本及模型配置的交互与视觉方案，形成一致的布局和状态反馈。
- [ ] 实现 React Web 与 Markdown 编辑器，接入 P2 文件与选区契约；重点处理选区、光标、保存反馈、长文本阅读和键盘操作。
- [ ] 接入 P1 会话、模型、流式消息、工具状态与停止接口；等待、生成、完成、失败和中断均有清楚反馈。
- [ ] 接入 P3 候选差异、采纳/拒绝、版本冲突和回退，清楚区分候选稿与正式正文。
- [ ] 接入核心参考材料、五栏人物卡、大纲和技能管理；P4—P6 额外功能待后端分别验收后再补充界面。
- [ ] 完成加载、空内容、错误和重试等常用状态；保留未提交输入，刷新后从接口读取已有会话和已保存结果。
- [ ] 使用真实后端和固定联调小说贯通全流程；发现必要接口缺口时同步修订契约并补充接口回归。
- [ ] 在主要桌面窗口尺寸检查布局、可读性、焦点和长文本滚动；执行关键浏览器流程测试及人工体验评审。

验收：

- 作者能独立完成“建立/导入小说 → 编辑 → 选材 → 生成 → 比较 → 采纳/拒绝 → 回看版本 → 导出”。
- 编辑位置、选区与保存状态清楚；生成内容逐步显示，工具执行有反馈，停止后状态及时更新，失败有可执行的下一步。
- 作者能辨认使用了哪些资料、AI 改了哪里、内容是否已写入正文，并能拒绝或回退操作。
- 流式更新不打断正在进行的编辑，不强行改变作者主动浏览的位置；常用操作不要求反复切页找入口。
- 空状态、长文稿、生成失败和版本冲突有完整交互；常用键盘操作、焦点及文字对比度经过检查。
- 产品功能全部接入真实接口，前端不直接调用 Pi 或本地存储；接口回归与关键浏览器测试通过。
- 人工连续创作评审记录操作阻碍并完成修正；视觉一致性、编辑体验和交互反馈单独验收，不能仅凭页面能打开或接口返回成功通过。

主要位置：apps/web、web/features/library、manuscript、assistant、proposals、story-bible、style、tests/e2e。进入 P8 前先完成前端功能及体验验收。

## 12. 交付顺序

1. P0 验证 SDK 版本与真实模型、工具、会话。
2. P1 封装通用 Agent 后端和统一接口，以 HTTP / SSE 测试验收。
3. P2—P3 完成小说数据与创作后端闭环，以连续接口用例验收。
4. P3 核心接口与必要模型质量验收通过后，P7 完成前端体验设计、实现、接入和用户操作验收。
5. P8 完成本地可靠性与受控试用；P4—P6 额外后端能力在前端之后按需求补充，不阻塞核心前端。
6. Electron 后续安排。

## 13. 完成标准与范围

- 文档状态与实测一致，不因方案确定就标记验证完成。
- 后端阶段以接口交付为准；核心 P3 通过后，P7 集中实现前端；界面体验和后端能力分别验收。
- 前端不复刻后端业务规则；接口契约更新时同时更新测试、说明和调用方。
- SDK 已有能力优先接入，不重复开发循环、会话持久化、压缩和重试。
- 业务测试聚焦保存、版本、跨书隔离、来源与采纳；模型效果使用真实样本评测。
- 不新增当前没有实际需求的框架、包和持久化表。
- 正文版本与候选稿是业务数据；普通对话等待是下一条消息，两者不强行归为统一任务引擎。

当前不安排 LangGraph、独立 Worker、任务队列、持久化 token 事件回放、自动步骤恢复或通用检查点系统。以后有明确功能需求再评估，不预设一定需要。

首版不做多人实时协作、复杂剧情分支、微服务、多 Agent 平台或模型微调。P4—P6 目标保留为后续规划，核心前端不依赖其完成。
