# Plotloom 小说创作 Agent 架构方案

初稿日期：2026-11-16；修订日期：2026-11-17。状态：SDK 1.5.2 的本地及真实模型接入验收通过，P0 完成。应用后端与前端尚未初始化；实测进度见 [P0 验证记录](p0-validation.md)，可视化说明保留架构规划阶段快照。

## 1. 目标与运行前提

Plotloom 是以小说项目为中心的 AI 创作工作台。作者不必反复解释背景，AI 能结合当前章节、设定与样文辅助创作。

已确认：
- 应用和数据全部在用户本机运行，允许调用云端模型 API；发给模型的上下文会离开本机。
- 开发阶段只考虑 Web；后续通过 Electron 打包桌面交付，复用同一套页面与本地核心。
- 单作者、多本小说；优先普通文件，允许 SQLite，不要求安装独立数据库服务。
- 以 Pi coding-agent SDK 为接入入口。Agent 循环、会话、工具机制、压缩、取消和有限重试优先直接复用。
- 自研集中在后端接口、小说业务和前端体验，不先建立通用工作流引擎。
- 先完成 AI 后端封装和统一接口，通过接口测试后再集中开发前端；前端体验单独验收。
- 生成内容先成为候选稿，作者采纳后才形成正式正文版本。

实施顺序：P0 SDK 验证 → P1 通用 Agent 后端与接口 → P2 小说资产后端 → P3 创作后端闭环 → P4—P5 记忆与检索后端 → P6 风格反馈及整体接口验收 → P7 前端体验设计、实现与接入 → P8 本地受控试用。Electron 后续交付。

当前无业务代码；不存在 .cursor/rules，本轮无可用 .mdc 规则；未找到 space/README.md、space/guanwenbo/plan 或 space/guanwenbo/memory。

## 2. 最小架构与职责

最终产品调用链：**Web 创作工作台 → 本机统一接口 → Pi SDK / 小说业务 → 云端模型或本地数据**。P1—P6 先由接口测试客户端验证后端，P7 再接入 Web。

| 部分 | 负责什么 | 实现方式 |
| --- | --- | --- |
| Web 页面（P7） | 编辑器、会话、资料、候选对比、模型配置、状态反馈 | React + TypeScript + Vite，集中实现并验收用户体验 |
| 本机接口 | 接收操作、维护当前 SDK 会话实例、转发流式事件、读取会话快照 | Node.js + Fastify，薄接入代码 |
| Pi 适配 | 创建/打开会话、发消息、订阅事件、停止，配置工具和提示词 | 直接调用 coding-agent SDK |
| 小说业务（P2 起） | 正文、版本、提案、采纳、设定、上下文选择 | 项目用例和业务工具 |
| 本地数据 | Pi JSONL 保存会话；小说数据按实际需要使用文件 / SQLite | 复用 SDK，业务仓储按需实现 |
| Electron（后续） | 窗口、启动本地核心、文件对话框、安装包 | Electron + Electron Forge |

API 与 Pi 在同一本地核心进程中运行。P1 不创建独立 Worker、任务队列、SQLite 运行表、事件回放库或检查点执行器。浏览器重连以重新读取会话消息和当前状态为主，不要求回放每个流式 token。

## 3. Pi 已有能力与自研范围

### 3.1 直接复用

SDK 指 @earendil-works/pi-coding-agent；pi-agent-core 和 pi-ai 是其下层能力，不另行搭建第二套循环。[R1][R2][R3]

| 需求 | Pi 提供的机制 | 我们的工作 |
| --- | --- | --- |
| 云端模型、多轮对话、流式响应 | 模型配置、prompt、事件订阅 | 接配置与界面 |
| 自动工具调用与继续回答 | Agent 工具循环、参数 Schema 校验 | 编写具体业务工具 |
| 创建、列出、打开、继续会话 | SessionManager、JSONL 持久化 | 指定目录并接会话列表 |
| 停止、追加要求、排队追问 | abort、steer、followUp | 按需接按钮与输入 |
| 长对话压缩 | SDK 自动压缩与配置 | 配置和展示，不重写压缩 |
| 临时失败重试 | SDK 有限重试及配置 | 直接复用，不叠加同类重试 |
| 系统提示、Skills、模板、材料注入 | 资源加载与扩展机制 | 写产品内容及材料选择逻辑 |
| 工具状态、错误、用量 | SDK 事件及模型用量信息 | 转发和展示 |
| 少量会话关联状态 | 扩展 appendEntry，可读取已保存自定义条目 | 按需保存候选选择状态；恢复解释逻辑由扩展实现 |

以上来自官方文档，不代表已验证当前发布包和 Windows 运行组合。[R2][R4][R5][R6] P0 固定实际可运行版本。

### 3.2 等待与恢复的明确范围

“读取资料 → 给出候选 → 用户选择 → 继续回答”按普通多轮对话实现：候选作为回复保存，本轮结束；用户选择成为下一条消息。重启后重新打开该会话即可继续。[R5]

需要按钮式选择时，界面将选项转换为下一条输入；只有确有结构化状态需求，才使用 SDK 自定义条目。不要为普通追问建立独立任务状态机。[R4]

本轮正式收窄旧方案的验收：
- 要求打开已保存会话继续对话，以及 P3 重新查看已保存候选。
- 不要求崩溃后自动续跑剩余步骤，不要求从中断 token 继续。
- 未完成请求显示中断，由用户决定是否重新发起。
- 不要求持久化每个流式事件；浏览器断线重新读取当前消息与状态。

### 3.3 需要自研的内容

P1：本机统一接口、SDK 薄适配、只读测试工具、提示词配置和 HTTP / SSE 接口测试。

P2—P3：小说与章节数据、保存和版本接口、设定工具、候选稿采纳/拒绝与上下文组织；通过接口完成创作闭环。

P4—P6：长篇检索、人物知情与来源追踪、风格反馈后端及接口评测。P6 整体接口验收后，P7 集中实现所有前端功能与体验；P8 完整产品试用。

工具的业务动作由项目编写，注册、调用和参数格式校验复用 Pi。小说工具经业务用例读资料或创建提案，不直接替作者采纳正文。

### 3.4 统一接口与前端接入边界

同一本机服务按会话、小说资产、创作提案、记忆检索和风格反馈提供接口。先定义核心用户操作、所需数据与状态，再形成请求/响应和 HTTP / SSE 事件契约；前端不直接使用 Pi 内部类型、文件或数据库。

P1—P6 每阶段交付接口说明、可执行请求示例、测试数据和公开接口回归。验证普通请求之外，还要验证流式内容、工具状态、停止、结束、错误及重新查询。真实模型连通性与效果另有实测记录。

P6 通过建书到生成、采纳、回退、导出的完整接口用例，交付联调数据与配置说明后进入 P7。P7 先完成交互和视觉方案，再实现页面并接真实接口；编辑手感、选区与保存反馈、生成状态、候选对比、来源解释和连续操作单独验收。实际交互需要新增接口字段时，同步更新契约与回归测试。

以下章节描述最终产品行为；其中页面和按钮均在 P7 实现，P2—P6 先提供相应数据与操作接口。

## 4. 小说资产与记忆模型

建议把记忆分成五类。正式正文及作者确认的设定是可追溯的创作资产；摘要、向量和模型提取结果是带版本的派生数据。

| 记忆类型 | 内容 | 使用方式 |
| --- | --- | --- |
| 小说设定 | 世界规则、人物身份、地点、组织、道具、作者确认的真相 | 当前任务必须遵守的约束 |
| 剧情状态 | 已发生事件、人物关系、地点、伤势、物品归属、角色知情状态 | 按目标场景重建，而不是取整本书的最新值 |
| 剧情计划 | 大纲、未来事件、伏笔回收安排、备选方向 | 给规划步骤使用；给写作步骤提供允许暗示与禁止揭示项 |
| 文风记忆 | 作者样文、作品风格、叙事视角、对白方式、已确认偏好 | 按场景选取样例和写作要求 |
| 工作记忆 | 当前请求、临时方案、运行消息、中间草稿、审校结果 | 仅在当前任务或显式延续的任务中使用 |

### 4.1 人物不能只存一张静态卡片

人物档案拆为稳定属性与随剧情变化的状态：

- 稳定属性：身份、核心欲望、恐惧、价值取向、惯用表达。
- 状态变化：所处地点、身体状况、能力、关系、持有物、当前目标。
- 知情与信念：某角色在什么场景获知什么，认为其是真是假，来自亲见、转述还是误判。

例如，作者知道“甲是叛徒”，乙到第 20 章才发现。写第 12 章乙的视角时，上下文不能把该真相作为乙已知信息；规划步骤仍可读取真相，用于安排伏笔。

将客观事实、角色信念和文本中的陈述分别建模。例如“不可靠叙述者声称门被锁住”是一条陈述，不直接等同于世界事实。

### 4.2 时间与版本必须分开

每条剧情事实至少关联：

- 书籍、实体、属性/关系及值。
- 来源正文版本、稳定段落 ID、引用片段。
- 叙事位置：读者在哪个章/场景看到或获知。
- 故事时间：事件在故事世界中的发生顺序，支持未知和相对先后。
- 有效区间与知情主体：在何时成立、哪些角色已经知道。
- 状态：候选、已确认、有冲突、已撤销；提取器与规则版本。

倒叙中“读者刚看到”不等于“事件刚发生”。上下文编译器需要同时接受目标叙事位置、故事时点和视角人物，不能仅按章节编号过滤。

第一版保留单一正式稿线与历史版本，不实现复杂的平行世界分支编辑。备选剧情属于提案，不能进入正式事实索引。

### 4.3 防止生成内容污染记忆

建议采用以下闭环：

1. 导入或保存正文版本，记录来源与内容哈希。
2. 后台提取事件、实体、状态变化与摘要，并附来源引用。
3. 提取出的结构化断言先作为候选；作者可以批量确认。
4. 用户采纳 AI 文本后，新的正文版本才进入正式检索范围；被拒绝的候选稿保持隔离。
5. 摘要等派生信息可以自动更新，但必须标注来源版本，不能覆盖已确认且冲突的设定。
6. 发现正文与设定冲突时展示两处证据，由作者选择改正文、改设定，或保留为有意矛盾。

为了避免确认负担，首版优先展示关键人物变化、硬设定冲突和新增重要实体，支持批量审核；未确认提取结果可作查找线索，不能悄悄升级为硬约束。

原文删除、改写或历史版本恢复后，相关摘要、向量、事实来源和上下文缓存需要失效。依赖关系按源版本记录，后台重建时只发布与当前版本匹配的结果，过期结果不能覆盖新结果。

## 5. 上下文编译：每次任务如何知道该知道的事

P3 先按作者选择读取材料；以下完整上下文编译能力在 P4—P5 逐步实现。输入包含书籍、目标场景/选区、任务类型、视角人物、当前正文版本和用户要求；输出一个可追溯、受预算约束的上下文包。

处理顺序：

1. 固定任务的数据快照，明确写哪一段、写到哪个时间点。
2. 从结构化数据读取当前场景人物、有效状态、世界规则和必要关系。
3. 优先纳入当前段落、邻近正文、相关原文证据，补充章摘要和卷摘要。
4. 使用实体名称/别名、关键词与语义检索查找相关片段，按书籍、版本、时间、确认状态和可见性过滤。
5. 检索去重并排序；硬约束不能只靠相似度召回。
6. 对不同角色步骤生成不同视图：规划可见未来计划，写作只获得当前允许表达的信息与保密要求。
7. 加入匹配当前场景的作者样文及可执行风格要求。
8. 按模型窗口预留系统提示、工具定义、工具结果、输出和安全余量，裁剪低相关资料。
9. 保存上下文条目、来源版本、选择原因和用量，便于复查。

长篇分层建议为段落/场景 → 章节 → 卷 → 全书。摘要用于导航和压缩，重要细节回到原文取证。初版按场景与段落切块并保留上下文边界，避免只按固定字数切断对白。

建议的优先级：作者显式约束和当前选区 → 视角/人物/世界硬约束 → 必要原文证据 → 场景计划 → 风格样例 → 远距离补充材料。若连必要材料都超过预算，应缩小生成范围或拆分场景，并在界面说明。

中文检索在 P5 结合真实样本验证名称别名、分词和召回效果。优先评估本地方案，向量索引及 embedding 届时选型；不预设 PostgreSQL、pgvector 或独立向量数据库。

检索为空或证据不足时，允许 Agent 表达未知、补查或提出新设定候选；不要把“没查到”解释成“可以随意修改既有事实”。

写作界面应允许展开“本次参考”，展示所用章节、人物状态、设定与风格样例，并允许作者临时固定或排除材料。

## 6. 创作流程：提示词、工具与普通应用调用

P3 用提示词、业务工具和必要的顺序调用实现续写与改写；不单独设立通用编排层。规划、写作、审校是同一 Agent 可执行的任务，不要求独立 Agent 或常驻服务。

| 用户任务 | 应用行为 |
| --- | --- |
| 查询设定/回顾剧情 | 通过工具读取材料，回答并显示来源 |
| 头脑风暴 | 提供设定与目标，输出备选方案，作者下一轮选择 |
| 局部改写 | 提供选区与要求，生成候选，检查后展示差异 |
| 续写场景 | 提供上下文与样文，生成并检查候选，由作者采纳 |
| 生成章节（P6） | 按场景组织生成，候选互相参考，采纳前与正式资料隔离 |
| 小说导入（P4） | 预览切章并保存原稿，再提取摘要和候选事实 |

候选内容保存后结束当前生成，等待作者操作。采纳是普通业务请求，检查基础版本后提交；拒绝不修改正式正文。

网络临时失败使用 SDK 有限重试。审校后的自动修订在业务需要时限定轮数，不构建通用调度系统。中断后由用户重新发起未完成请求，已保存会话和候选可重新打开；不承诺自动续跑步骤。

## 7. “文学性”和作者风格如何进入系统

把“减少 AI 味”转成作者可判断的具体要求，而不是一个总开关。建议围绕作者样文、场景目标和可解释审校建立反馈闭环。

### 7.1 三层风格配置

| 层级 | 内容 | 为什么需要 |
| --- | --- | --- |
| 作者偏好 | 喜欢的表达、常见修改、明确禁忌 | 跨会话保留个人选择；跨作品应用需作者主动启用 |
| 作品风格 | 叙述人称、视角距离、语言时代感、对白与描写倾向 | 同一作者的不同作品可能有不同声音 |
| 场景要求 | 情绪、节奏、冲突、潜台词、信息揭示程度 | 打斗、日常与离别不应使用同一套表达密度 |

样文优先使用作者自行标记的段落，并按场景类型检索。风格描述与样文共同提供，避免只给抽象形容词。不要把所有文学表达都等同于多加修辞。

可执行要求示例：当前使用乙的有限视角；不要直接解释甲的真实意图；通过动作与对白表现怀疑；保留对白中的停顿；按作者样文控制段落节奏；结尾是否收束由场景目标决定。

### 7.2 生成与审校策略

生成前定义“场景中发生什么变化”。生成后分别检查：

- 情节与动机：行为是否符合当前目标、已知信息和人物经历。
- 表达：是否过度解释情绪、对白声音是否同质、比喻是否空泛、段落是否重复承担同一功能。
- 叙述：视角是否漂移、是否提前揭示秘密、是否违背作者选择的叙事距离。

这些是建议的审校维度，不是普适文学规则。检查应引用问题片段，提出局部修改理由；除非作者要求，不默认整章重写。

把采纳、拒绝、人工修改记录为反馈。一次改动不能自动认定为长期偏好；重复出现或由作者确认后，才更新对应作品的风格配置。作者可以查看、纠正和关闭这些偏好。

### 7.3 如何验证有效

建立覆盖续写、对白、视角、伏笔、人物动机和改稿的代表性样本。使用同一基础模型比较普通聊天、仅正文检索、完整上下文与风格工作流，隔离模型选择的影响。

事实指标：设定冲突、人物知情泄漏、时序错误、检索证据覆盖率。

创作指标：作者盲评偏好、采纳率、采纳前修改量、完成可用场景所需时间。保留任务类型和作者差异，不能只看一个总分。

运行指标：首段响应时间、整步完成时间、每千字模型成本、失败与恢复情况。

模型审校可辅助定位问题，但文学质量最终以作者判断为主。本方案不承诺架构本身能保证文学性，也不将所谓 AI 文本检测分数作为验收目标。微调留待积累经授权且质量稳定的修改样本后评估。

## 8. 核心数据模型与正文写入

建议的逻辑实体如下，实施时可合并部分表，不要求逐项建立独立服务。

| 实体 | 关键内容 |
| --- | --- |
| Novel | 作者归属、书籍信息、当前设定版本、当前稿线 |
| Chapter / Scene | 章/场景顺序、视角、故事时间、当前正文版本 |
| ManuscriptRevision | 编辑器文档、派生纯文本、父版本、来源、内容哈希 |
| StoryEntity | 人物、地点、组织、物品及别名 |
| Assertion / CharacterKnowledge | 事实或信念、主体、有效时段、来源、确认状态 |
| PlotPlan / PlotThread | 剧情目标、伏笔、计划回收位置、已发生与计划状态 |
| Summary / RetrievalChunk | 来源版本、粒度、正文位置、词项/向量与索引版本 |
| StyleProfile / StyleExample | 生效范围、样文、偏好、作者确认记录 |
| Proposal | 基础版本、修改范围、替换内容、关联检查、采纳状态 |
| 会话关联 | Pi sessionId、所属小说及必要的业务引用；不复制完整会话历史 |
| Feedback | 采纳/拒绝/手工修改、原因、关联提案与样文 |

正文建议保存结构化编辑器文档，并生成检索纯文本。Tiptap 官方支持 JSON 持久化且推荐该形式；具体段落 ID、差异应用和版本机制需要由项目实现。[R8]

提案保存基础版本 ID、段落 ID、目标文本哈希和替换内容。采纳时在事务中检查版本：

1. 基础版本匹配，创建新正文版本，更新当前指针及提案状态。
2. P4—P5 再按源版本标记摘要、事实和索引待更新，由本机应用执行或由作者触发重建。
3. 基础版本不匹配，展示差异，让作者重新应用或重新生成，不覆盖期间的手工修改。
4. 以采纳请求 ID/提案 ID 做幂等约束，重复点击或重试不产生重复版本。

发布索引时校验目标源版本。生成时记录输入版本；正文、关键设定或风格规则变化后，尚未采纳的产物标记为需要重新检查。

## 9. 技术与本地交付

以下是简化方案的建议包组合，具体版本由 P0 接入验证后固定。

| 范围 | 建议包或机制 | 何时引入及原因 |
| --- | --- | --- |
| 前端 | react、react-dom、typescript、vite | P7，集中实现 Web，后续 Electron 复用 |
| 本机接口 | fastify；HTTP + SSE | P1，先提供统一接口与测试，P7 接页面 |
| Agent | @earendil-works/pi-coding-agent | P1，复用会话和执行能力 [R2] |
| 会话持久化 | SDK SessionManager / JSONL | P1，不复制到另一份数据库历史 [R5] |
| 提示词和工具 | SDK 配置、资源加载、自定义工具 | P1 提供测试工具，P3 增加小说工具 |
| 编辑器 | @tiptap/react、@tiptap/pm、@tiptap/starter-kit | P2 确定正文数据契约，P7 接入编辑器 [R8] |
| 小说存储 | node:fs/promises；按需 SQLite / better-sqlite3 | P2 按正文、版本和提案需要选择；不为 P1 会话提前建数据库 [R7][R9] |
| 日志与验证 | Fastify 日志；vitest、@playwright/test | P1—P6 接口测试；P7 浏览器流程与体验验收 |
| 桌面交付 | electron、@electron-forge/cli | 后续实现；原生依赖兼容性届时验证 |
| 工程组织 | pnpm workspace | 包有实际代码和调用方时才创建 |

数据归属：
- 会话消息和工具结果由 Pi JSONL 持有。
- 少量与会话绑定的自定义数据可用 SDK 扩展条目保存，不重复维护权威状态。
- 小说正文、设定、版本和提案由业务仓储持有。正文格式、SQLite 表和文件划分在 P2 根据实际编辑与保存需求确定，不提前固定哈希内容仓库。
- 索引在 P4—P5 按源版本生成，可重建；向量包和 embedding 届时验证。
- 模型凭据由本地核心持有，不交给页面；开发期可使用环境变量。

后端阶段由测试客户端访问本机接口，P7 再由浏览器接入；后续 Electron 负责窗口与本地核心生命周期。首版不要求 Docker Compose、PostgreSQL、Redis、pg-boss、LangGraph 或独立 Worker。只有具体业务证明需要，才重新评估。

保留实际的数据保护：正式稿保存版本、采纳检查来源版本、重复采纳不重复提交、不同小说不串用。备份覆盖业务数据和会话文件。

## 10. 实施顺序与验收

按可验证成果推进，不在团队规模与模型条件未知时承诺工期。

| 阶段 | 实现范围 | 验收重点 |
| --- | --- | --- |
| P0：SDK 接入验证 | SDK 发布版本、真实模型、工具、会话与配置验证 | 固定可运行版本，形成 P1 接入清单 |
| P1：通用 Agent 后端与接口 | SDK 会话/工具/停止/配置、HTTP / SSE 契约 | 无前端也可用公开接口对话、停止并继续历史会话 |
| P2—P3：小说资产与创作后端 | 正文、设定、上下文、续写/改写、提案与版本接口 | 完整接口闭环；旧提案不覆盖新稿，采纳可回退 |
| P4—P5：记忆与检索后端 | 导入、摘要、人物知情、检索、冲突与来源接口 | 固定样本与接口测试验证时点、来源和失效行为 |
| P6：风格反馈与整体接口验收 | 风格、审校、反馈接口与完整回归 | 效果评测、接入文档和联调数据齐备，后端验收通过 |
| P7：前端体验设计、实现与接入 | 完整创作工作台，接入 P1—P6 接口 | 连续创作、编辑体验、生成反馈、候选对比和视觉分别验收 |
| P8：本地受控试用 | 本机启动、备份恢复、连续创作试用 | 完整产品回归通过，数据可以取回 |

| 后续按需 | 全书影响分析、更多导出格式、多人协作、复杂分支、模型微调 | 有明确用户需求和收益证据后再投入 |

P3 创作后端即加入最小作者样文与风格要求，并通过接口产物验证生成效果；P6 负责系统化反馈和整体接口验收。P7 才形成可直接操作的创作产品并验证前端体验。P0—P1 不需要提前建立小说领域模型。

按对应阶段验收的场景（后端阶段通过接口验证，页面交互在 P7 验证）：

- 第 20 章才获知秘密的人物，在第 12 章不能使用该信息。
- 同一人物在不同章节的伤势和物品归属应按剧情时点重建。
- 拒绝一段候选稿，其中的新人物和事件不进入正式记忆。
- 修改来源正文后，旧摘要/向量/候选断言不会被当作最新证据。
- 生成期间作者修改正文，采纳旧提案不能静默覆盖修改。
- 本机服务重启后能打开已保存会话和候选；重复采纳不会重复提交正文。
- 同一作者两本风格不同的小说，样文和偏好不会自动串用。
- 作者能看到本次写作用到了哪些材料，并纠正错误记忆。

实施重点顺序：SDK 验证 → 通用与小说后端能力 → 接口和效果验收 → 前端设计、实现与联调 → 完整产品试用。优先复用通用机制，将自研投入集中在小说专属能力上。
