# 通用 Agent、小说业务与可导入 skill：工程方案讨论

日期：2026-11-17；更新：2026-11-18。状态：通用核心定位、skill 管理与外部导入边界已确认；P2/P2.1 已实现验收，见 [P2.1 实施计划](p2.1-implementation.md) 与 [验收](../p2.1-validation.md)。下文保留设计依据，小说工具与实际创作效果在 P3 验证。

业务依据：[小说工作区场景](p2-novel-assets.md)。用户提出“提供 skill 管理，把生成小说做成内置 skill，包含写小说需要的 tool call”。下文保留这个产品方向，并明确执行边界。

## 1. 已确认方向与工程建议

用户已确认定位：**通用 Agent 核心，先把小说创作这个垂直场景做好。** 当前自定义 skill 主要用于文风提取、对白打磨等辅助写作；技能管理也可支持未来其他领域，例如辅助记账，不应把所有 skill 限定为小说流程的补充。

小说首版建议采用“现有 Pi Agent + 内置写作 skill + 少量业务工具 + 工作区与候选服务”。通用性体现在会话、工作区关联、技能管理与工具接入上；人物卡、大纲和小说采纳规则由小说业务承担，不能成为其他领域聊天的默认规则。记账目前只是扩展方向，不建设记账功能或通用业务插件框架。

- skill 负责写作方法、操作步骤、资料使用和自检规则。
- 工具向模型提供确定的读取和候选提交能力。
- 业务后端负责文件归属、版本、候选、差异和采纳，不能靠 skill 文本保证数据不被覆盖。
- 前端通过公开 HTTP / SSE 使用业务后端，既不直接执行 skill，也不直接读写本机文件。

产品上可以把“写小说”展示成一个完整的内置技能。工程上允许说明文档、人物卡模板和工具适配代码随同一功能交付，但工具必须由应用明确注册；在 SKILL.md 里写一个工具名字不会自动提供实现，也不能授予写入正式稿的权限。

## 2. Pi 支持情况与现有差距

核对基准为仓库固定的 `@earendil-works/pi-coding-agent@1.5.2`，并参考 2026-11-17 查阅的上游官方文档；不能把官方 main 分支等同于本地已接入行为。

| 项目 | 证据与结论 |
| --- | --- |
| skill 资源 | Pi 支持 SKILL.md、参考材料和按需加载；本地安装包的 `docs/skills.md` 说明自动选择可能遗漏，可显式调用 `/skill:name` |
| 自定义工具 | SDK 提供 `customTools`，扩展也可注册工具；本项目 `AgentOptions.tools` 已支持传入工具定义 |
| 当前 skill 接入 | P2.1 使用独立应用技能库，按请求注入摘要并提供 read_skill；getSkills() 仍为空，避免启用默认编码资源机制 |
| 当前资源隔离 | 资源加载器刻意不读取开发者个人技能、开发规则或默认编码工具，应保留这种明确的资源范围 |
| 当前会话工作区 | SDK cwd 仍为统一服务目录；小说归属已用自定义条目保存，P3 再将其绑定到小说工具作用域 |
| 加载细节 | 本地 `dist/core/system-prompt.js` 的默认 skill 列表注入依赖名为 `read` 或 `bash` 的读取工具；现有只有自定义工具名，不能只填充 `getSkills()` 就假定自动发现生效 |

已实现：小说入口默认配置写作 skill，缺少声明工具时报告不可用；对可运行技能注入摘要，显式选择时加载正文，参考材料通过受限 read_skill 获取。没有开放通用 shell 或任意文件读取。请求快照及下一请求刷新已通过固定 SDK 版本的独立接口测试。

## 3. 职责划分

| 层 | 承担的职责 | 原因 |
| --- | --- | --- |
| Pi Agent | 对话、模型、工具循环、流式输出、停止、压缩、会话持久化 | 已有 P1 基础，继续复用，不另造 Agent 执行器 |
| skill 管理 | 应用级管理内置、自定义和外部导入技能；展示来源、说明与依赖，按工作区或聊天启用、按需加载 | 不依赖小说实体，未来领域技能复用同一机制 |
| 内置写作 skill | 按大纲工作、读取相关卡片、引用历史原文、发现冲突先讨论、控制对白与情感表达、调用候选工具 | 这些是模型执行的创作方法，适合用可阅读说明和示例表达 |
| 工具适配 | 将模型参数转为业务调用，返回正文、版本、来源与候选结果 | 工具保持薄层，HTTP 与工具复用同一业务用例 |
| 业务服务 | 工作区识别、文件读写、候选与版本、采纳冲突、历史恢复、小说聊天关联 | 即使不用 AI，用户仍能独立管理、编辑和取回作品 |
| 前端 | 小说导航、聊天、编辑选区、差异显示、用户采纳 | 展示和操作基于公开契约，可独立替换 |

建议的数据流：

```text
聊天/选区请求 → 小说会话入口 → Pi + 已选 skill
                                  ↓ tool call
                            工作区/候选业务服务
                                  ↓
                         返回资料或已保存的候选

用户查看差异 → 采纳接口 → 业务服务重新校验 → 写入正式 Markdown
```

用户采纳与模型提交候选走不同入口。模型能“提出修改”，不应获得能绕过用户采纳的写入工具。前端和工具均只调用业务服务，不各自实现一份文件规则。

## 4. 内置写作 skill 的组织建议

先做一个覆盖当前完整流程的 `novel-writing`，按任务读取参考文件，不提前拆成规划、对白、人物、情感等多个协作 Agent。

建议包含：

- `SKILL.md`：何时使用、输入要求、读取资料、冲突讨论、生成与局部修改、如何提交候选。
- `references/character-card.md`：用户提供的五栏人物卡与行为一致性核对方法。
- `references/writing-review.md`：剧情推进、情感表达、对白区别和删减冗余的检查要点。
- `references/tools.md`：工具参数、来源引用、候选提交示例和错误处理。
- `assets/character-card.md`：可供整理人物资料的 Markdown 模板。

P2.1 已交付 SKILL.md、references/character-card.md 和 assets/character-card.md；其余参考按 P3 实际工具需要补充。它们是 Plotloom 产品资源，不是安装到 Codex 的技能。具体人物资料与章节大纲属于小说工作区，不写进内置 skill，以免不同小说混用。

执行流程建议为“读取材料 → 检查具体冲突 → 必要时提问并结束本轮 → 用户答复后继续 → 起草与自检 → 提交候选”。普通讨论继续复用多轮会话，不引入持久化工作流引擎，也不使用 Pi 的终端 UI 作为 Web 的交互接口。

skill 里的自检属于模型行为要求，应以样例评测；它不能保证识别所有语义矛盾，也不能替代后端确定性的版本检查。

## 5. 首版工具建议

名称仅用于讨论，尚不是接口契约。

| 工具 | 输入/输出要点 | 用途 |
| --- | --- | --- |
| `list_documents` | 列出当前小说的文档，包含种类、相对路径和名称 | 找到角色、章节、大纲，避免模型猜路径 |
| `read_document` | 读取某文档或范围，返回原文、版本及范围信息 | 获取五栏卡、当前稿和指定章节片段 |
| `search_documents` | 在本小说或指定文档内按字面词句查找，返回命中位置和片段 | 支持定位用户指定的旧章节情节；首版无须向量库 |
| `propose_change` | 目标文件、基础版本、修改范围或新内容、修改说明、来源引用 | 新建或修改只产生候选，不写正式稿 |

skill 参考资料的读取另由受限资源入口承担，可复用 SDK 资源机制；不能把技能路径和小说路径混成任意文件读取接口。

角色卡、章节、大纲都能通过同一套文档读写候选能力处理，无需为每个字段各建一个 tool。后续只有出现实际业务差异才增加工具。

发现人物冲突时，模型可以直接在聊天中解释并等待用户，不必为了普通问答新增 `ask_user` 工具。正式稿写入、采纳、拒绝和历史恢复作为用户操作接口，不作为写作模型的自主工具。

工具执行时由服务端绑定工作区；不信任模型自己提供的根目录。在小说入口核对小说与工作区归属，文档引用仍需核对是否属于当前小说，防止跨书读取或提交候选。通用技能管理无需理解“角色”“章节”等小说概念。

## 6. 文件、候选和版本建议

### 6.1 正式文件是当前内容依据

Markdown 是正式作品的当前内容。数据库或内部元数据可保存工作区登记、会话关联、候选与历史，但不能维护另一份与磁盘竞争的“当前正文”。

聊天历史继续由 Pi JSONL 持有，小说业务只记录 `novelId / workspaceId ↔ sessionId` 关联，不复制完整消息。切换小说导航不能悄悄更改已有聊天的归属。

Git 并非用户使用前提。P2 已选普通文件实现内部历史：JSON 保存清单及候选状态，Markdown 保存独立版本快照；没有 SQLite 或通用存储替换框架。实现与验证见 [P2 验收](../p2-validation.md)。

### 6.2 候选是独立业务对象

建议候选保存：目标工作区与文件、生成时的原稿快照/版本、候选结果、选区位置（如有）、引用的资料版本、创建时间和状态。用户已确认逐处采纳，还需记录每处修改的标识及处理状态，支持部分采纳后继续审阅。

差异由后端基于原稿和候选计算，供任何前端显示；模型的文字总结不能充当实际 diff。用户可以用确定性测试直接提交候选来验证后端，阶段验收不必依赖模型输出恰好符合要求。

P2 选区使用“文件版本 + UTF-16 半开范围 + 选中文本”，不得切开代理对。Markdown 不依赖编辑器私有段落 ID；后端只应用声明范围，防止越过选区修改。

### 6.3 采纳与外部编辑

- 采纳前重新读取目标文件，与本候选原稿及已记录采纳结果构成的预期当前内容比较；新建文件候选也要检查目标是否已由用户创建。
- 基础不一致时保留两份内容并返回冲突，不自动合并。
- 同一处修改重复采纳保持幂等；用户双击不能重复提交，不能以整份候选作为唯一的采纳状态。
- 对角色卡、大纲等实际读取过的依赖，P2 保存版本；变化时返回 REFERENCE_CONFLICT 并保留候选，要求重新核对后创建新候选。
- 文件监听只负责及时提示，正确性检查仍放在读取和提交入口。

需要专门验证的现实限制：单纯“检查哈希后 rename”不能证明外部编辑器不会恰好在两步之间保存；应用内锁也无法约束外部进程。实施前应针对 Windows 与常用外部编辑器验证文件提交和冲突处理，明确遇到同时写入时的行为，不能把它描述成已解决的强事务。

用户已明确要求**逐处采纳**，此前按整个文件采纳的建议不再适用。

P2 在后端维护每处修改的稳定标识、原稿范围、替换内容和采纳结果，按行分组相邻增删。只发布用户选择的修改；以基础原稿和已采纳各处重建预期内容，前方修改造成的偏移不依赖前端旧行号。

同一候选内已知的部分采纳与外部编辑必须区分：前者允许继续处理剩余修改，后者继续按已确认的冲突规则提示用户。部分采纳后拒绝其余修改不撤销已采纳内容；若需撤回，走独立历史恢复操作。需验证乱序采纳、文本重复、前方增删引起偏移、重复请求、部分采纳后重启及外部编辑等实际场景。

## 7. skill 管理范围：已确认

用户已确认：**管理内置 skill，支持自定义及从外部下载导入的 Markdown skill；工具由项目提供。** 首版不包含自动执行外部脚本或加载任意自定义工具代码的插件能力。

### 7.1 管理与导入范围

1. 查看内置、自定义和导入 skill 的名称、用途、来源、内容、声明的依赖与生效状态。
2. 新建、编辑和移除自定义 Markdown skill，校验名称和说明等必要格式。
3. 兼容 Agent Skills 目录组织：以 SKILL.md 为入口，导入时保留引用的参考材料与模板，不能只复制入口文件。
4. 格式兼容不等于运行兼容。依赖项目未提供工具、执行环境或外部服务的技能，应明确说明缺少的能力，不宣称所有外部技能开箱即用，也不自动开启脚本执行。
5. 需要调整内置方法时，建议复制为自定义版本，避免产品升级覆盖作者修改。

导入方式的首版建议为选择已下载的完整技能目录。是否还支持压缩包、Git 仓库地址或应用内直接下载，尚未确定；不因用户允许外部导入就默认包含在线包管理系统。依赖检查可展示声明并验证已知工具，不能承诺从任意自然语言技能中静态识别全部运行依赖。

### 7.2 安装、启用与加载

已确认采用以下方向：

- 应用级安装：技能导入一次，在统一技能库管理。
- 按工作区或聊天启用：小说创作使用写作及辅助技能，其他聊天选择对应技能；不把记账等无关技能默认用于小说。
- 按任务加载：只向模型提供当前可用技能的简要说明，需要时读取详细内容，保留用户显式选择入口。
- 小说创作入口默认使用内置写作技能；这是小说入口的装配行为，不是通用 Agent 的全局固定系统提示。

2026-11-18 用户已确认并实现：聊天默认跟随工作区，单独设置数组完整覆盖，null 恢复跟随，空数组关闭全部。消息 skillIds 仅明确加载本轮已启用技能，不修改配置；管理产品界面留待 P7。此前“辅助技能只能本次请求生效”的建议不再作为已定边界。

### 7.3 运行边界与扩展原则

首版先完成已确认的技能管理、导入与小说场景验证；在线市场、依赖安装、复杂技能继承或自动工具热插拔不列入当前实现。原因是当前还没有这些机制的实际调用需求。

技能启停和版本变更已实现从下一次请求生效，运行中的请求固定其资源快照；不能承诺停用后历史聊天会自动遗忘已经加载的指令。实际权限仍由每次请求装配的工具集合和业务后端控制，`allowed-tools` 等文本声明不能当作正式稿写入授权。

例如，文风提取技能可以复用文档读取与候选能力；未来记账技能若需要可靠保存、汇总账目或接入账单服务，需由项目提供相应工具。新增方法可通过技能扩展，新增实际业务操作需补齐工具和业务能力。

后续验收至少覆盖：完整目录导入后引用材料可读；无效格式有明确诊断；缺失工具或运行环境不伪装成功；启用范围正确；小说候选采纳规则不因换技能而被绕过。工具正确性与技能实际效果分别验证。

## 8. 阶段拆分（2026-11-18 已同步路线图）

| 建议阶段 | 交付重点 | 为什么 |
| --- | --- | --- |
| P2 工作区基础（已完成） | 小说工作区、Markdown 读写、外部编辑识别、版本历史、候选/差异/采纳基础 | 先验证所有原稿操作；AI 和页面后续都可使用 |

候选逐处采纳、文件与历史存储及 P2 公开契约已实现并验收，旧 JSON 资产草稿已按用户确认清理。P2.1 技能与聊天关联也已验收；下一阶段为 P3 小说工具和真实创作闭环，之后再做 P7 前端，额外后端能力后置。
