# 小说工作区：已确认业务场景与验收草案

日期：2026-11-17；更新：2026-11-18。状态：核心方向及先后端闭环、再前端、后扩展的顺序已确认；P2 资产基础、P2.1 技能与聊天关联已验收，P3 小说工具/真实创作与产品交互尚未完成。

本文以用户本次讨论为依据。原先“每本小说一个 JSON 快照、正文采用带段落 ID 的编辑器 JSON”的方案已不符合确认后的 Markdown 文件工作区需求，不再作为实施依据。用户于 2026-11-18 确认此前 JSON 资产草稿无用，按 Markdown 重做，不保留兼容。

本文记录产品目标和已确认操作。涉及 skill 的工程建议见 [写作 skill 与工具架构讨论](novel-skills-architecture.md)。主架构与路线图已按此次确认收敛，具体实施见 p2-implementation.md。

## 1. 目标与首版边界

用户已有角色人设和详细章节大纲。过去在聊天产品里写新章节，需要反复提交人设，生成结果常需大量人工修改。目标是让这些资料持续复用，围绕大纲写出强剧情、强情感、少废话、人物说话有区别的正文。

- 交互以类似 Codex 的对话工作区为参考，增加小说管理和小说资料。
- 每本小说对应用户选择的本地工作区，章节等资料为真实 Markdown 文件。
- 首版只考虑详细章节大纲；情节安排、伏笔和回收由用户在大纲中写明。
- 不将全书自动规划、自动伏笔管理、全书语义检索或知识图谱作为当前前提。
- 创作质量由实际样稿和用户修改反馈验证，不能以“有 skill”或接口成功代替效果验收。
- 产品采用通用 Agent 核心，当前先实现小说垂直业务。技能管理支持内置、自定义及外部导入 Markdown skill；未来可以扩展其他领域，但当前不建设记账等额外业务。

## 2. 已确认的资料与归属

| 对象 | 规则 |
| --- | --- |
| 小说 | 对应一个本地文件夹；不同小说的资料与聊天按归属区分 |
| 章节正文 | 每章一个 Markdown 文件，用户可在应用内或外部编辑器中修改 |
| 章节大纲 | 用户直接发到聊天；整理成独立 Markdown 候选，采纳后保存，后续按同样流程修改 |
| 角色卡 | 每个角色一个 Markdown 文件，使用五栏人物卡 |
| 作品写作要求 | 保存作品共同的写作要求，避免每章重复交代 |
| 聊天 | 可在小说下创建并按小说分组，同时保留最近聊天入口；不要求聊天历史也是 Markdown |
| AI 候选 | 与正式文件分开保存，支持查看差异、逐处采纳或拒绝 |
| 历史版本 | 保留应用实际观察到和提交过的版本，用于查看和恢复 |

## 3. 五栏人物卡

五栏保留为自然语言 Markdown，不强迫用户把每个子项都填满。

| 栏目 | 内容与写作约束 |
| --- | --- |
| 性格特点 | 区分外显性格和内在性格。通过压力、亲密、关键选择等情境表现拉扯，避免解释性旁白和生硬露馅 |
| 愿景 | 明示追求有优先级；潜意识驱动有触发条件。以冲突中的选择表现排序，反常行动要有已交代的触发与代价 |
| 社会背景 | 阶层、职业、教育、成长、文化和关系影响措辞、手段、风险选择及资源；不只贴背景标签 |
| 外表特点 | 相貌、衣着、动作、装备和物件服务识别与剧情，与经历、背景或愿景关联 |
| 特殊性 | 按需记录心理特质、语言习惯、禁忌、固定小物、执念、技能差异、关系雷点、伤痕经历或身份遮掩，避免堆砌 |

核心核对：此刻行为是否与“性格 × 愿景 × 背景”一致？若不一致，大纲是否已经给出合理的触发与代价？

五栏是写作依据，不是每个桥段都必须展示的清单。不要求每章固定制造一种人格矛盾，不机械重复口癖或外貌。人物声音需结合关系、身份和当下情绪体现。

角色卡里的深层设定是作者资料，不代表其他角色都知道，也不代表正文应该直接解释出来。

## 4. 主要操作场景

### 4.1 开始一章

1. 用户选择小说工作区，新建或继续该小说的聊天。
2. 在聊天中发送本章详细大纲和补充要求。
3. AI 读取相关角色卡、作品要求，以及本次写作需要的已有正文。
4. 有明确冲突时先讨论；不存在待澄清冲突时，形成大纲文件或正文的候选。
5. 用户查看候选差异；采纳才写入正式 Markdown，拒绝不改原稿。

大纲保存与正文生成是否需要两个独立采纳步骤，或允许一次请求生成多个独立候选，仍待交互讨论；不得默认必须先采纳大纲才能讨论正文。

### 4.2 引用历史章节

用户可以提出“这里回忆第三章码头告别”。AI 读取该章并寻找相关原文，与当前大纲一起考虑，不凭聊天印象编造细节。

- 已确认：支持用户指定章节及情节的相关片段进入上下文。
- 建议：返回所引用的章节、片段和版本，便于用户核对。
- 建议：找不到时说明；有多个无法判断的候选片段时提问。
- 默认参考已采纳的正式文件，未采纳候选不自动变成历史事实。

### 4.3 大纲与人物设定冲突

例如，大纲要求某角色做出明确违背其禁忌的行为，又未交代触发原因。

AI 应说明大纲的具体要求、冲突的人物卡条目以及缺少的解释，与用户讨论。确认前不能自行补动机、触发、代价，不能擅自修改大纲或角色卡来消除冲突。

可以提供明确标为建议的解决思路；建议不等于用户已确认的设定。只有受到冲突影响的创作需要等待，不扩展为每次生成都必须走形式化审批流程。

### 4.4 选区修改

用户选中某段文字，在聊天中提出修改要求。AI 参考选区、附近内容和相关资料，形成针对该范围的候选。范围以外的正文保持原样；若必须扩大修改范围，应说明并先讨论。

用户查看前后差异，采纳后写入。相同文字在章节中出现多次时，必须依据本次选择的位置识别目标，不能简单替换所有同名文本。

### 4.5 外部手动编辑

正式 Markdown 以磁盘上的实际内容为准。重新打开、准备写作或采纳候选时，应重新读取文件；应用缓存不能覆盖外部修改。

候选记录生成所依据的原稿。若用户期间用其他编辑器修改了目标文件，采纳时提示冲突，保留现有文件和候选，让用户决定后续处理，不直接覆盖或自动合并。

该规则同样适用于角色卡、大纲和作品写作要求。应用只记录实际读取到的历史内容，不能宣称捕获了外部编辑器每一次中间保存。

### 4.6 历史与恢复

用户可查看已记录版本并恢复历史内容。恢复本身形成新记录，恢复前的内容仍可查看。恢复时也需检查当前文件，避免覆盖恢复页面打开后发生的外部修改。

### 4.7 逐处采纳（已确认）

用户明确选择逐处采纳。一份候选包含多处修改时，可以分别决定接受或拒绝，不要求整章或整个文件一次性接受。

- 接受某处修改，只将该处写入正式文件；未采纳的部分继续保持原文。
- 每处修改有独立处理状态，部分采纳不能将整份候选标记为已采纳。
- 同一候选内，采纳前一处造成的正文变化，应由系统正确记录；其余修改仍可继续审阅，不能把已知采纳误判成外部修改。
- 期间发生外部手动编辑，仍需执行冲突检查，不得借逐处采纳自动覆盖或合并外部改动。
- 重复点击已采纳的一处，不重复写入；重启后保留各处处理状态。

P2 已采用后端按行分组的差异：相邻增删合为一处，中间有未变行则分开；范围使用 UTF-16 半开区间，位置基于基础原稿。候选未采纳部分继续通过聊天打磨的交互仍属建议，不能默认为用户已经确认全部操作细节。

## 5. 工作区组织示例（不强制目录名）

```text
小说工作区/
├─ 写作要求.md
├─ 角色/
│  ├─ 约翰.md
│  └─ 其他角色.md
├─ 大纲/
│  ├─ 0001-第一章.md
│  └─ 0002-第二章.md
└─ 章节/
   ├─ 0001-第一章.md
   └─ 0002-第二章.md
```

采用可直接阅读的文本结构，是为了让用户能够离开应用继续编辑和备份。P2 接口接受工作区中的任意合法 `.md` 相对路径，不依赖示例中的中文目录名。工作区、候选和历史清单采用服务数据目录中的内部 JSON，正文快照为独立 Markdown；小说聊天关联在 P2.1 实现。

## 6. 验收场景草案

| 场景 | 应观察到的结果 | 所属能力 |
| --- | --- | --- |
| 创建或打开小说工作区 | 能定位实际文件夹并识别约定资料；重开仍可读取 | 工作区基础 |
| 同一本小说创建两个聊天 | 按小说分组，最近列表仍可访问；聊天归属不随切换界面漂移 | 聊天关联 |
| 两本小说具有同名角色文件 | 读取、生成和采纳始终定位所属小说，不串用资料 | 归属校验 |
| 从聊天整理大纲 | 候选未采纳前磁盘上不出现正式大纲；采纳后可读取 | 候选与文件 |
| 创建新章节候选 | 展示新增文件差异，采纳后文件才出现 | 候选与文件 |
| 拒绝未采纳修改或停止生成 | 不写入未采纳内容，不撤销此前已明确采纳的内容；完整候选与未完成输出状态可区分 | 候选与 Agent |
| 明确人物冲突 | 指出具体冲突并等待讨论，不擅自编造解释或修改资料 | 写作 skill 的行为评测 |
| 用户指定历史情节 | 实际读取相关章节，生成可核对的引用；找不到不编造 | 资料读取与写作评测 |
| 修改选区 | 非选区文字不受影响；重复句子的定位正确 | 选区与候选 |
| 生成候选后外部改稿 | 采纳失败并提示冲突，手工稿与候选均保留 | 并发与文件 |
| 角色卡或大纲在生成后变化 | 采纳返回 REFERENCE_CONFLICT，保留候选；重新核对后生成新候选 | 来源版本，P2 已实现 |
| 五处修改只采纳其中两处 | 正式稿仅包含已选两处修改，其他位置保留原文；候选显示部分采纳 | 逐处采纳 |
| 先采纳前方修改再采纳后方修改 | 前方字数变化不导致后方错位，也不误报外部冲突 | 修改定位 |
| 两次采纳同一处修改 | 不重复写入、不重复创建版本 | 幂等采纳 |
| 部分采纳后外部改稿再采纳 | 提示冲突并保留当前稿和剩余候选，不自动覆盖外部修改 | 并发与文件 |
| 应用重启 | 正式资料、候选各处处理状态、版本和小说聊天关联仍可读取 | 持久化 |
| 恢复历史正文 | 新建恢复记录，恢复前稿仍可查询 | 版本 |
| 原稿导出和备份 | 取回真实 Markdown、历史及候选；资产恢复已验收，不包含 Pi 会话与凭据 | P2 已实现，完整产品备份在 P8 |

写作效果需用固定大纲、角色卡与人工判读验证；文件正确性、版本冲突、归属和幂等应通过独立接口测试验证。全部新增公开业务接口还需登记到接口试验台并实测，遵守项目交付要求。

## 7. 后续讨论及阶段安排

已确认上述核心业务，以及“通用 Agent 核心、小说垂直业务；应用级管理内置/自定义/外部导入 Markdown skill，按工作区或聊天启用，按需加载；工具由项目提供”的首版方向。外部导入保留参考材料与模板，缺少工具或环境时明确提示，首版不自动执行外部脚本。

用户已明确要求逐处采纳。P2 已确定内部存储、差异分组与选区契约，并保持文件命名自由；技能启用的具体交互仍在 P2.1/P7 细化。

建议先建设工作区、文件读取、版本和候选采纳基础，再让内置写作 skill 调用这些能力。界面实现可后置，但数据和接口应按这些真实操作设计。候选基础放在 P2，技能管理与聊天关联放在 P2.1，P3 完成写作接入及核心整体验收后进入前端。

P2 已通过独立接口与试验台验收，见 [P2 验证记录](../p2-validation.md)。核心闭环还需 P2.1/P3；表中聊天、模型行为和产品交互条目不能因资产基础通过而标记完成。
